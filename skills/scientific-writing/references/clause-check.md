# 子句检查（clause check）

来源：intent_loop 的 spec 评审方法（把自然语言规范的可判真单元与代码的可执行单元一一对上）+ `semantic-clause-decomposition` 技能（裁掉形式逻辑记法，只留可操作部分）。

## 0. 唯一判据

**每个「当…则…」「A 与 B 都…」「每个 / 任意 / 仅当」都能被拆成一个能单独回答「实现做到了吗」的 clause；每个 clause 都能指到一个实现点和一个测试点。**

指不出来的 clause，要么是背景修辞，要么是**没人实现的需求**——后者是最有价值的发现。

## 1. 拆句：一个 clause = 一个可独立判真的实现点

把规范句切成 clause，判据是：**这个 clause 能单独回答「代码做到了吗」**。修辞、动机不参与判定，只做背景。

实例（intent_loop）：

> spec §10：「a single-pair checkpoint resumed with `--all-pairs` → `ConfigError` (I3); an all-pairs checkpoint resumed without `--all-pairs` → `ConfigError`.」

拆成：

- clause (a)「single-pair checkpoint + `--all-pairs` ⇒ `ConfigError`」→ 实现存在 → ✅
- clause (b)「all-pairs checkpoint + 单对模式 ⇒ `ConfigError`」→ 守卫整个在 `if all_pairs:` 内，此分支从不执行 → 🔴 缺陷

**同一个 bug 在「实现层」与「规范自述层」各记一条**，因为修法不同：一个改代码，一个改措辞。只记一条，修完代码后规范里的假话会留下来，下一轮继续骗人。

## 2. 对称句必须双侧分别验证

凡出现「A ⇒ X; B ⇒ X」「同样」「both directions」「symmetric」——**每一侧都是独立断言，只验一侧 = 未验**。

- 把每一侧写成独立 clause，各自找实现点与测试点
- 推演到可观测后果，不写「可能有问题」
- 常见缺口：实现只做一侧，测试也只测一侧

## 3. 量词与辖域：配置项的作用域是一等公民

凡「上限 / 预算 / 重试次数 / 超时」类配置，必须写清：

1. 量词对象：每个 X 一个？整场一个？
2. 是否重置：在哪里重置？
3. 与其它计数的关系

把两种读法回译成可区分的条件：

- 期望读法（∀pair）：`∀ pair p: rounds(p) ≤ max_rounds`
- 实际读法（Σcampaign）：`Σ_p rounds(p) ≤ max_rounds`
- 二者在 `max_rounds=5`、pair 数 > 2 时**行为不同** ⇒ 真歧义

**交叉算术自检**：用文档自己的估算数字去验配置上限。例：spec 自己估计「11 pairs × ~2.5 rounds ≈ 27 rounds」，而 `max_rounds=5` ⇒ 第 3 个 pair 起被静默跳过。矛盾即缺陷。

## 4. 条件守卫：两侧都要执行

规则：凡「若 P 则报错」的守卫，必须确认 **P 与 ¬P 两侧都执行**；写进 `if P:` 内部时，¬P 分支根本没有机会触发。

- 守卫语句的缩进层级 = 被保护流程的**上一层**
- 反向用例（¬P）必须有测试
- 用否定辖域描述：规范说 `∀mode: mismatch ⇒ error`，实现成 `all_pairs: mismatch ⇒ error`，修法自然是把 ¬ 的作用范围扩到整句

## 5. 断言反空转：测试必须能红

每个测试必须能回答「**什么情况下它会失败**」。三查：

1. 断言里有没有 `or` 兜底（`assert not exists() or ...` 可能恒真）
2. 期待的异常是否真的会被抛
3. 修复前它是否真的会红（placebo vs regression guard）

复核时给「反空转声明」：说明在旧语义下该测试确实失败。

## 6. 措辞与预设：一个词也能构成一个 clause

动词 / 名词选择本身携带断言：

- `becomes` 预设「原本是硬编码」——若原本没有，应写 `new`
- `all` 预设「每个实例都完整」——partial dict 会打破它
- 未发生的检验写 `None`，不写默认值（`p: 1.0` 会被读成「检验跑了且 p=1」）
- 同一个词在两处有各自的判定式时，必须交叉比对；不一致不一定修，但必须登记

## 7. finding 五段式

每个发现固定五段：

1. **Location**：plan 行 + spec 节 + 决策号
2. **Evidence**：引原文 + 对照实现
3. **Why**：为什么是缺陷；推演到具体行为与数字
4. **Why-the-test-missed**：为什么现有测试没抓到（单点 bug → 测试设计缺口）
5. **Fix**：选项 A / B + 推荐

编号稳定（F1..Fn），严重度四档（🔴 CRITICAL / 🟠 HIGH / 🟡 MEDIUM / 🟢 LOW）；**撤回项保留在表里划掉**，防止下一轮复活。

## 8. 与 semantic-clause-decomposition 的映射（裁剪版）

| 技能步骤 | 写作 / 评审动作 |
|---|---|
| 剥壳（量词词 / 否定词 / 连接词） | 把「每个 / 所有 / 仅当 / 否则 / 同时 / 同样」圈出来，一个词一个 clause |
| 量词（域 + 辖域） | 配置项作用域与重置点：按 pair / 按 campaign / 共享 |
| 否定与联结（¬ 辖域；and/or/unless） | 守卫在 `if` 内还是外；反向分支是否存在 |
| 回译（真值条件 + 排除的读法） | 把 clause 回译成「实现必须满足的断言」+「一个必须失败的测试」 |
| 候选门槛 1（存在模型使两读法真值不同） | 只有能让两种实现产生**不同行为**的歧义才算真歧义 |
| 候选门槛 2（句法依据） | 歧义必须有文本依据，不能是「我觉得可能」 |
| 输出契约紧凑形 | Evidence → Why → Test-miss → Fix → Unhandled |

**加一步「锚定」**：每个 clause 必须指向实现点（文件:行 / 函数 / 配置字段）与测试点。

## 9. 交付前自查

- [ ] 每个规范句已拆成 clause
- [ ] 对称句两侧各有实现与测试
- [ ] 每个上限 / 预算写清量词对象与重置点
- [ ] 用文档自己的估算数字做过交叉算术
- [ ] 每个守卫在 ¬P 分支也可触发
- [ ] 每个测试能说出「什么情况下会红」
- [ ] 未发生的量写 `None`，不写默认值
- [ ] finding 五段齐全，编号稳定，撤回项保留
